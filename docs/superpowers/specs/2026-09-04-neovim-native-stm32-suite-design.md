# Neovim-native STM32 suite design

Date: 2026-09-04  
Status: approved in conversation, awaiting review of this written spec

## Decision

`nvim-stm32` will grow into a complete STM32 development environment for
Neovim. ST's STM32CubeIDE for Visual Studio Code is a feature reference, not a
runtime dependency. The plugin will not require the ST extension pack, read VS
Code configuration, use the ST bundle manager, or introduce a separate
`stm32` command-line application.

The plugin will own STM32 project discovery, device knowledge, workflow
planning, safety checks, process lifetime, and user-facing commands. It will
use ordinary command-line tools and optional Neovim integrations for jobs they
already perform well.

## First priority

The existing CSSE3010 firmware projects and the user's NUCLEO-F429ZI are the
first release gate. Broader STM32 support comes after this path works from end
to end.

The first supported environment is:

- The 13 independent firmware folders under
  `~/Documents/University/CSSE3010/repo`
- CMake preset projects generated by STM32CubeMX
- STM32F429ZITx on a NUCLEO-F429ZI
- ARM GNU Toolchain 15.2
- STM32CubeProgrammer 2.23, `st-flash`, and OpenOCD 0.12
- macOS on Apple Silicon
- The user's normal Neovim configuration

The coursework repository is a read-only test corpus. Plugin work never edits
it. Tests may configure and build its projects because that only writes ignored
build output.

Work on other boards must not weaken this path. A general abstraction only
lands when the F429 fixtures, real project builds, and existing command behavior
remain green.

## Goals

The plugin will provide these workflows without leaving Neovim:

- Discover and describe STM32 projects from the current buffer
- Configure, build, clean, rebuild, and select build configurations
- Find fresh ELF, BIN, HEX, MAP, and related artifacts without guessing
- Report flash and RAM use by section and memory region
- Discover probes and select them by stable serial number
- Flash, verify, mass erase, reset, and halt
- Monitor UART, RTT, SWO, and semihosting output where the selected backend
  supports them
- Launch or attach a debugger
- Set breakpoints, step, inspect variables and registers, read memory, and show
  disassembly
- Inspect SVD-defined peripheral registers
- Decode Cortex-M faults
- Show RTOS threads and kernel objects when reliable data is available
- Coordinate bootloader/application and heterogeneous multicore projects
- Create a bare CMake project and import existing CubeMX projects or firmware
  examples
- Run host, target, and hardware-in-the-loop test tasks

The plugin will keep simple projects configuration-free. It will ask for or
persist overrides only when the source tree cannot answer a question safely.

## Non-goals

- Reimplement STM32CubeMX peripheral and clock configuration
- Download or update compilers, debug servers, CMSIS packs, or vendor tools
  without an explicit user command
- Accept third-party licenses on the user's behalf
- Depend on internal CubeProgrammer or CubeMX database formats
- Parse or execute VS Code `tasks.json`, `launch.json`, or extension files
- Match the visual layout of STM32CubeIDE or VS Code
- Support STM32MP Linux development as if it were an MCU workflow
- Promise every debug feature through every probe backend
- Support Windows in the first release

## Reference feature set

ST's current extension divides its product into editor UI, downloadable CLI
bundles, and CMSIS-Pack device support. It covers project creation and import,
clangd, CMake, build analysis, probe management, ST-LINK and J-Link debugging,
serial output, peripheral data, RTOS data, and multicore projects. The official
[extension overview](https://marketplace.visualstudio.com/items?itemName=stmicroelectronics.stm32-vscode-extension)
and [documentation index](https://dev.st.com/stm32cube-docs/stm32cubeide-vscode/latest/en/index.html)
define the comparison set.

`nvim-stm32` will implement equivalent development jobs using Neovim concepts.
It will not copy the extension's package manager or editor architecture.

## Architecture

The core has no required Lua plugin dependency. Optional integrations load only
through guarded adapter modules.

```text
current buffer
    |
    v
workspace resolver
    |
    +--> Project
           |
           +--> Image: application / bootloader / CM7
           +--> Image: validation / CM4
                    |
                    v
              operation planner
                    |
          +---------+---------+
          |                   |
      tool drivers        inspectors
          |                   |
          +---------+---------+
                    |
              process manager
                    |
          Neovim UI and adapters
```

The source tree will move toward these module boundaries:

```text
lua/nvim-stm32/
  model/          project, image, artifact, probe, result validation
  discover/       roots, project signals, image grouping, artifacts
  catalog/        offline device index, CMSIS-Pack providers, provenance
  build/          CMake and Make adapters, configurations, target enumeration
  operations/     build, analyze, flash, debug, monitor, test plans
  drivers/        tool-specific pure command builders and parsers
  process/        jobs, pipelines, streams, cancellation, cleanup, locks
  session/        selected context and last successful results by project root
  inspect/        size, map, memory, registers, SVD, faults, RTOS
  ui/             commands, selectors, output, quickfix, status
  integration/    optional Snacks, Telescope, nvim-dap, Overseer, compiler.nvim
  health/         project, tools, probes, adapters, and capability reporting
```

The current modules will migrate in small commits. Compatibility wrappers will
keep `detect.target()`, `:STM32Info`, and `:STM32Build` working during the move.

## Data model

### Project

A project owns build configuration and an ordered set of images.

```lua
Project = {
  id = "absolute normalized root",
  root = "/path/to/firmware",
  kind = "cubemx-cmake",
  build = {
    adapter = "cmake-presets",
    configurations = {},
    selected = nil,
  },
  images = {},
  flash_order = {},
  provenance = {},
}
```

### Image

An image represents one independently built and programmed firmware image.

```lua
Image = {
  id = "cm7",
  name = "application-cm7",
  build_target = "application_CM7",
  target = {},
  artifacts = {},
  flash = {
    address = nil,
    order = nil,
  },
  debug = {
    core = "CM7",
    port = nil,
    reset_policy = "halt",
  },
}
```

Single-core projects contain one image. Bootloader/application workspaces and
dual-core devices contain several. The model supports several images from its
first migration, even though the F429 path is the first acceptance target.

### Target

Target identity separates silicon, cores, board intent, and the observed probe.

```lua
Target = {
  identity = {
    cpn = nil,
    cmsis_device = nil,
    family = nil,
    aliases = {},
    build_defines = {},
  },
  platform_kind = "mcu",
  cores = {
    {
      id = "CM4",
      architecture = "cortex-m4",
      fpu = "fpv4-sp-d16",
      memory_regions = {},
      svd_path = nil,
      debug = {},
    },
  },
  board = {},
  debug_profiles = {},
  provenance = {},
  capabilities = {},
}
```

Memory stays as named regions. A single `ram_kb` value cannot describe CCM,
shared memory, core-specific views, or discontinuous regions.

### Artifact

Each artifact records what produced it. This prevents an ELF from another preset
or core from being flashed. A successful no-op build may leave the file timestamp
unchanged, so freshness means the plugin validated the artifact after the last
successful build operation for that configuration. It does not require a newer
timestamp.

```lua
Artifact = {
  image_id = "application",
  kind = "elf",
  path = "/absolute/path/application.elf",
  configuration = "Debug",
  build_target = "application",
  modified_ns = 0,
  build_id = nil,
}
```

### Probe and session

A probe records adapter identity and observed state. It does not stand in for a
board. An external ST-LINK can be attached to any compatible board.

Session state is keyed by project root. It records the selected project, image,
configuration, probe, and last successful artifacts. It remains in memory unless
the user explicitly writes project configuration.

## Project and image discovery

Discovery still begins at the current buffer and stops at the Git root. That
behavior is central to repositories containing many firmware folders.

Root discovery and image discovery become separate operations. Generated nested
CMake directories must not become project roots merely because they contain a
`CMakeLists.txt`.

Project evidence includes:

- All `.ioc` files, including `Mcu.CPN`, `Mcu.UserName`, `Mcu.Name`,
  `ProjectManager.DeviceId`, family, and board fields
- Startup files
- Linker scripts
- Compiler defines, CPU flags, and FPU flags
- CMake presets and CMake File API replies
- Make targets and output conventions
- User or project overrides

The resolver retains every signal and its source. It groups signals by image
instead of taking the first match. Exact identifiers beat grouped CubeMX names.
Compiler flags measured for an image beat family defaults.

For CMake, the plugin will use preset inheritance and the configured `binaryDir`.
After configuration, it will read the CMake File API codemodel to map executable
targets to artifacts. Recursive ELF globbing remains a fallback for Make projects
and never chooses between several candidates without an image mapping.

## Device and board catalog

The current hand-maintained two-character family table is not enough. It assigns
one core to a whole family and names OpenOCD scripts that may not exist in the
installed OpenOCD release.

Resolution uses these layers in order:

1. Explicit user and `.nvim-stm32.json` overrides
2. Evidence from project files
3. A small versioned offline silicon index shipped with the plugin
4. Installed CMSIS device and board packs
5. An installed CubeMX database as an optional recognition provider
6. Capabilities discovered from the selected backend installation
7. Chip identity observed during an explicit connection

Detection performs no network requests. Missing SVD or OpenOCD data removes the
specific capability, not the whole target.

The offline index will be generated from pinned, license-audited CMSIS Device
Family Pack metadata. It stores identifiers, aliases, processor topology, memory
regions, compile defines, and logical SVD references. It does not redistribute
vendor binaries or SVD files without confirmed permission.

The public CMSIS-Pack schema supports device variants, multiple processors,
per-processor memory, debug ports, algorithms, and SVD references. See the
[device description](https://open-cmsis-pack.github.io/Open-CMSIS-Pack-Spec/main/html/pdsc_devices_pg.html)
and [board description](https://open-cmsis-pack.github.io/Open-CMSIS-Pack-Spec/main/html/pdsc_boards_pg.html).

OpenOCD board and target scripts remain executable backend profiles. The plugin
checks that a chosen script exists in the active OpenOCD installation before it
offers that profile.

## Project configuration

Simple projects need no plugin file. A complex project can add
`.nvim-stm32.json` at its root.

```json
{
  "version": 1,
  "images": [
    {
      "id": "bootloader",
      "buildTarget": "bootloader",
      "flashAddress": "0x08000000"
    },
    {
      "id": "application",
      "buildTarget": "application",
      "flashAddress": "0x08020000"
    }
  ],
  "flashOrder": ["bootloader", "application"]
}
```

The schema will reject unknown versions and invalid addresses. The plugin will
offer a command to write this file from the resolved session. It never creates or
changes it during ordinary discovery.

Project-local Lua is not executed. JSON keeps configuration reviewable and avoids
running code from an untrusted repository.

## Operation planning

Every command resolves to an immutable operation plan before it starts:

```lua
OperationPlan = {
  id = "unique operation id",
  kind = "flash",
  project_id = "...",
  images = {},
  commands = {},
  probe = {},
  ports = {},
  locks = {},
  reset_policy = "run-after-verify",
}
```

Each command is a structured specification rather than a shell string:

```lua
CommandSpec = {
  argv = { "cmake", "--build", "..." },
  cwd = "/project",
  env = {},
  image_id = "application",
  lifecycle = "short",
  ready_pattern = nil,
  timeout_ms = nil,
}
```

`:STM32Plan` shows the resolved images, artifacts, commands, probe, ports, and
reset policy without executing anything.

The process manager supports short jobs, ordered pipelines, long-running streams,
server readiness, cancellation, output limits, and owned-process cleanup. It
returns a handle immediately. Closing an output window does not silently abandon
a child process.

All build and debug children receive the configured toolchain directory at the
front of `PATH`. No command goes through a shell unless a user-defined task
explicitly requests one.

## Workflows

### Build and analysis

Build selects a real CMake configure or build preset, resolves inheritance,
configures, builds the requested targets, and reads fresh artifacts from the
CMake File API. Make remains supported through explicit adapter rules.

Compiler diagnostics populate quickfix while the complete output remains in a
reusable operation buffer. Analysis uses `arm-none-eabi-size`, the ELF, and the
MAP file to report sections, symbols, and use of named memory regions.

### Flash, erase, reset, and probe management

Flash backends remain pure command builders. The initial order is configurable:

1. A user-selected backend
2. STM32CubeProgrammer
3. `st-flash`
4. OpenOCD

J-Link gains a programming backend when its command-line tools are present.

Multi-image flash validates every artifact and address before touching the board.
It writes in project order, verifies every image, then applies one final reset
policy. A failure reports exactly which images were written and leaves the target
halted when the backend permits it.

Probe enumeration records serial numbers. Probe firmware updates are separate,
confirmed operations. Passive discovery does not connect, reset, or halt the MCU.

### Monitor

UART selects among platform serial devices and configures the line before
streaming. RTT uses the chosen debug server's TCP channel. SWO and semihosting
appear only when the backend advertises and passes the required setup.

Long-running monitors own their process or socket and stop when requested. The
output buffer can remain open after the stream ends.

### Debug

The preferred structured debugger is `nvim-dap` with Eclipse CDT's standalone
`cdt-gdb-adapter`. The adapter drives ARM GDB through MI and connects to a remote
GDB server. It does not require VS Code or a VS Code extension. The adapter
supports breakpoints, variables, register scopes, memory access, and disassembly.
See the [adapter repository](https://github.com/eclipse-cdt-cloud/cdt-gdb-adapter).

The installed ARM GDB accepts MI3 but was built without Python and rejects its
native DAP interpreter. The plugin therefore never treats GDB or OpenOCD as a DAP
adapter.

Neovim's built-in `termdebug` is the zero-install fallback. It uses the same
server plan and ARM GDB. A configured standalone DAP adapter can replace CDT
through the integration interface.

Debug server drivers cover:

- OpenOCD by default
- ST-LINK GDB Server when installed
- J-Link GDB Server when installed

Each driver provides argv, a readiness pattern, GDB port, target type, setup and
reset commands, side channels, and capabilities. The plugin owns only the server
process it starts.

`:STM32Debug` builds, flashes, starts the target halted, and launches the frontend.
`:STM32Attach` never builds, flashes, resets, or continues the target.

One GDB and one frontend session will be used for each heterogeneous core. The
termdebug fallback supports one active core. Multicore structured debugging
therefore requires the DAP path.

### Inspection

The plugin owns small buffers for registers, memory, disassembly, peripherals,
faults, and RTOS state. Reads go through the active debug adapter when possible
and through an auxiliary GDB connection only when the server supports it.

SVD resolution happens after device and core selection. A peripheral view shows
named registers, fields, access rules, and changed values. Writes require an
explicit edit action and respect read-only fields.

Fault analysis reads and decodes Cortex-M SCB fault registers, shows the exception
frame, PC and LR, backtrace, and nearby disassembly. The decoder is pure Lua and
fully testable without hardware.

RTOS threads first come from server-provided GDB threads. FreeRTOS and ThreadX
kernel-object views require version-aware readers and recognizable symbols. The
plugin reports an unsupported layout instead of displaying guessed data.

Live watch remains experimental. It is disabled by default, limited to globals
or fixed addresses, and offered only when the server supports background reads.
RTT or SWO is preferred for high-rate telemetry.

### Project and test tools

The plugin can generate a minimal bare CMake project from its own reviewed
templates. CubeMX project creation remains a CubeMX job. If CubeMX has a supported
CLI mode, the plugin may invoke it through an explicit command and then discover
the generated project.

Project import means discovery and optional generation of `.nvim-stm32.json`.
The plugin will not rewrite working CubeMX build files merely to fit its own
layout.

Test operations run project-defined commands and parse common formats. Host tests,
target tests over a probe or serial connection, coverage tools, and
hardware-in-the-loop tasks share the normal operation planner. Hardware tests are
never part of the default CI job.

## Error and safety model

Errors contain a stable code, a short message, operation and image identity, the
failed command, captured output, and a suggested fix. UI code formats errors but
does not infer their meaning from output strings.

Preflight checks happen before execution:

- Project and image selection are unambiguous
- Required tools are executable
- Artifacts belong to the selected configuration and are fresh
- Flash addresses are valid and non-overlapping
- A destructive operation has the required confirmation
- The selected probe is not owned by another plugin operation
- Required ports are free
- The backend supports the requested capability

A chip ID observed during an explicit connection is compared with project
identity. A mismatch blocks flash, erase, and debug launch unless the user makes
an explicit one-time override.

Only one operation owns a probe at a time. Server ports come from a reserved
per-session range and multicore ports cannot overlap.

Cancellation stops only processes and sockets created by that operation. The
plugin does not kill processes by a broad executable-name match. An external
process holding a probe produces a diagnostic with its known port or PID when
available.

No GDB server listens on a non-loopback interface by default. The
[OpenOCD GDB documentation](https://openocd.org/doc/html/GDB-and-OpenOCD.html)
explains that GDB server connections have no built-in authentication.

Missing hardware blocks only the hardware stage. It does not turn a successful
build or analysis into a failure.

## Testing

### Pure tests

Pure Lua tests cover:

- Project, image, artifact, target, probe, and result validation
- `.ioc`, startup, linker, CMake preset, CMake File API, MAP, SVD, and pack parsers
- Signal grouping, precedence, provenance, and ambiguity
- Command plans for every backend
- Address and memory-region validation
- Fault register decoding
- RTOS layout decoding for supported versions
- Project configuration schema and migration

### Process and integration tests

Fake executables and local TCP servers cover:

- Ordered jobs and streaming output
- Readiness detection and startup failure
- Cancellation, timeouts, bounded output, and cleanup
- Missing tools and malformed output
- Multiple probes and busy probes
- Partial multi-image flashes
- DAP adapter launch configuration
- UART, RTT, SWO, and semihosting streams
- Hardware disconnect and reconnect events

Fixtures cover single-core, multicore, bootloader/application, Make, plain CMake,
CMake presets, grouped MCU names, several ELFs, stale artifacts, and missing
metadata.

### Real project gate

Before hardware testing, every CSSE3010 firmware folder will be discovered from a
source buffer and configured with its real preset. Every buildable project will
build using the configured ARM toolchain. The plugin will associate each output
with the correct project, configuration, image, and memory map.

The current `s5/dt` project remains the fast real-project smoke test. Broader
tests run as an explicit local suite so normal plugin CI does not depend on a
private repository.

### Neovim UI gate

Headless tests verify command registration and callbacks. A normal Neovim instance
is controlled through its RPC socket to verify selectors, quickfix, output
buffers, cancellation, window closure, and optional integration behavior.

### CI

The required CI checks remain:

```sh
scripts/test.sh
stylua --check lua/ tests/
```

CI runs on Neovim stable and nightly. Optional dependencies are tested both
present and absent. Hardware tests are opt-in and never run on ordinary pull
requests.

### Hardware gate

After every software-only check passes, the user will connect the NUCLEO-F429ZI.
The hardware sequence is deliberately conservative:

1. Enumerate the probe and read its serial and firmware version
2. Connect without reset and compare the observed MCU
3. Read target voltage and basic device information
4. Build a known coursework image
5. Halt and reset without programming
6. Program and verify the known image
7. Reset and confirm expected firmware behavior
8. Open UART monitoring
9. Start a debug session and reach `main`
10. Exercise breakpoints, stepping, variables, registers, memory, and disassembly
11. Read one safe peripheral register through the SVD view
12. Exercise RTT or SWO only when the firmware supports it
13. Run erase testing last, followed immediately by restoring the known image

No broader board claim is made until this sequence passes repeatedly in the
user's normal Neovim setup.

## Delivery order

This program is too large for one branch. Each item gets its own design detail,
implementation plan, branch, tests, review, and merge.

### Track 1: make the current setup excellent

1. Project, image, artifact, and cancellable-process foundation
2. Correct CMake preset and File API behavior across the coursework corpus
3. F429 build analysis, flash, verify, erase, reset, and UART monitor
4. F429 debug launch and attach through CDT DAP with termdebug fallback
5. F429 registers, memory, disassembly, SVD peripherals, and fault analysis
6. Normal-Neovim verification, documentation, and hardware gate

Track 1 must finish before compatibility claims expand beyond the current board.

### Track 2: broaden STM32 project and board support

1. Generated offline catalog and installed CMSIS-Pack provider
2. ST-LINK and J-Link probe matrix
3. Bootloader/application and multicore project coordination
4. RTT, SWO, semihosting, and supported RTOS views
5. Bare project templates, import helpers, and test tasks
6. Family fixtures and opt-in hardware reports from additional boards

## Compatibility and migration

Existing setup options and commands stay valid through Track 1. Deprecations emit
one clear warning and remain supported for at least one tagged minor release.

The current `Stm32Target` shape remains available as a compatibility view of the
selected image. New code consumes `Project`, `Image`, and `Artifact` records.

The previous design's required `nvim-dap-cortex-debug` path is removed. Health
checks will report the independent CDT adapter, termdebug fallback, selected GDB
server, and missing capabilities separately.

CubeProgrammer remains a supported command-line backend. The plugin will resolve
an explicit path, `PATH`, and normal standalone installation locations. It will
not read an ST bundle manifest or treat the VS Code bundle manager as installed
state.

## Definition of done

Software-only work is ready for the board when:

- All repository tests and formatting checks pass
- All 13 current firmware folders resolve to the correct project and MCU
- Every buildable current project builds from Neovim with the chosen preset
- Artifacts and memory reports match direct command-line results
- Fake-tool tests cover every hardware command and failure path
- Debug configurations launch against fake or loopback servers
- A normal Neovim RPC test completes every non-hardware interaction
- `:checkhealth nvim-stm32` gives actionable results for the user's machine
- The README documents the exact current setup and optional dependencies

Track 1 is complete only after the NUCLEO-F429ZI hardware checklist passes in the
user's normal Neovim instance. Track 2 cannot regress that checklist.
